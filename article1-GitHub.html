Git and GitHub for DevOps: A Complete Tutorial

  • By Atul Kumar
  • November 01, 2025

1. What Git and GitHub are

Git is a distributed version control system used to track changes in files, collaborate, and manage history locally and across teams. (Source: GeeksForGeeks, W3School). Use Git for branching, staging changes, and creating commit history. (Source: GeeksForGeeks).

GitHub is a cloud hosting service built on Git that adds collaboration features: remote repositories, pull requests, issue tracking, actions (CI/CD), and code review interfaces. (Source: YouTube, GeeksForGeeks).

Sources used for foundational descriptions: the tutorial video and general guides (YouTube, GeeksForGeeks, W3School).

2. Setup and installation

Supported platforms

macOS, Linux, Windows. Installers and package managers are available: Homebrew (macOS), apt/yum (Linux), Git for Windows (includes Git Bash).

Quick install (commands)

# macOS (Homebrew)
brew install git

# Ubuntu/Debian
sudo apt update
sudo apt install git

# Windows
# Download Git for Windows installer and enable Git Bash.

First-time setup

Set identity (local machine):

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Configure helpful defaults:

git config --global core.editor "code --wait" # (or your editor)
git config --global color.ui auto

3. Core Git concepts and local workflow

Repository basics

  • Initialize a repo: git init
  • Clone a remote: git clone <repo-url>

Working areas

  • Working Directory: where you edit files.
  • Staging Area (index): where you prepare changes for commit.
  • Local Repository: where commits (history) are stored.

Typical local workflow (commands)

  • Check status: git status
  • See differences: git diff (unstaged) or git diff --staged (staged)
  • Stage changes: git add <file> or git add .
  • Commit: git commit -m "Clear, descriptive message"
  • Amend last commit (local only): git commit --amend --no-edit

Commit message guidance

  • Use imperative mood: "Add login validation"
  • Keep subject ˜ 50 characters; leave a blank line then details if needed.

Reference for basic Git usage and workflows: tutorial and guides (YouTube, W3School).

4. Branching and merging (practical DevOps patterns)

Creating and switching branches

  • Create: git branch feature/awesome
  • Switch: git checkout feature/awesome or git switch feature/awesome
  • Create + switch: git checkout -b feature/awesome

Merge vs Rebase (when to use)

  • Merge: preserves history as graph; good for feature integration and team contexts.
  • Rebase: linearizes history; useful for local cleanups and before merging to main.

Workflow example (feature branch -> main):

git checkout main
git pull
git checkout feature/awesome
git rebase main
# Resolve conflicts, then:
git checkout main
git merge feature/awesome

Deleting branches

  • Local: git branch -d feature/awesome
  • Remote: git push origin --delete feature/awesome

Branching and merging are core collaborative patterns emphasized in the source tutorial and best-practice guides (YouTube, GeeksForGeeks).

5. Remotes and GitHub collaboration

Basic remote commands

  • Add remote: git remote add origin <url>
  • View remotes: git remote -v
  • Push local to remote: git push -u origin main
  • Pull updates: git pull
  • Fetch updates without merge: git fetch

Forks, clones, and contribution model

Forking is common for open source: fork the repo on GitHub, clone your fork, create branches, push to your fork, and open a pull request against upstream. (Source: YouTube).

For internal teams, create branches in shared repo and use pull requests for review.

Pull requests (PRs)

Create PR on GitHub web UI: choose base (target) and compare (feature) branches.

PR checklist for maintainers:

  • Clear description and linked issue
  • Small, single-purpose changes
  • Passing CI and tests
  • Reviewers assigned and approvals collected

Use PR templates and issue templates in repo to standardize contributions.

GitHub-specific collaboration flow and PR best practices are covered in the original tutorial and extended here (YouTube).

6. GitHub features that accelerate DevOps

Issues and project boards

  • Use issues for tasks/bugs; label and assign.
  • Project boards (Kanban) help visualize progress.

Actions (CI/CD)

  • GitHub Actions triggers: push, pull_request, schedule.
  • Typical workflow: Build and test, Lint and static analysis, Run deploy step on successful main merges.
  • Store secrets in repository settings for secure deployment.

Releases and tags

  • Annotated tag: git tag -a v1.0.0 -m "Release 1.0.0"
  • Push tags: git push origin v1.0.0

Use GitHub Releases to attach binaries and changelogs.

These features are powerful for automating testing and deployment pipelines in a DevOps lifecycle (YouTube).

7. Branch protection, code review, and CI/CD policies

  • Protect main branches: require PR reviews, passing status checks, and up-to-date branch before merging.
  • Enforce signed commits or commit signing for stricter audit trails.
  • Automate checks: linters, unit tests, security scans (SAST), dependency checks.

Applying branch protection and CI gates forms the backbone of accountable and safe deployments in production.

8. Advanced topics for DevOps engineers

Git hooks (local and server-side)

  • Client hooks: pre-commit, commit-msg for linting and enforcing commit style.
  • Server hooks: pre-receive hooks for policy enforcement.

Large files and monorepos

  • Use Git LFS for large binaries; avoids bloating history.
  • For monorepos, consider sparse checkouts and careful CI optimization.

Submodules and subtrees

  • Submodules keep external repos as subfolders; manage with git submodule add/update.
  • Subtrees can be simpler alternative for vendor code.

Handling merge conflicts at scale

  • Use three-way merges, avoid huge long-lived branches, rebase frequently to keep conflicts small.
  • Use tooling (merge drivers, GUI tools) to resolve complicated conflicts.

9. Troubleshooting and recovery

  • Undo local changes: git checkout -- <file> (discard unstaged) or git reset HEAD <file> (unstage)
  • Revert commits: git revert <commit> (create new commit that undoes)
  • Reset (dangerous for shared history): git reset --hard <commit>
  • Recover deleted branch: git reflog to find commit; git checkout -b recovered <commit>

Include safe guidelines: prefer revert over reset on published history.

10. Best practices and workflow recommendations

  • Keep commits small and focused; one logical change per commit.
  • Write clear commit messages with a short subject and optional body.
  • Use protected branches and PR reviews to ensure code quality.
  • Run CI on every PR and require passing checks before merge.
  • Use feature flags and incremental rollouts for risky changes.
  • Automate releases and changelogs when possible.

These recommendations synthesize the tutorial's approach and common industry practices (YouTube, GeeksForGeeks).
